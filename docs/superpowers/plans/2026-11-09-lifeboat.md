# lifeboat Implementation Plan

> **For agentic workers:** execute inline with superpowers:executing-plans, task by task. Steps use
> checkbox (`- [ ]`) syntax for tracking. No per-task review; one review before submission.

**Goal:** a Hermes plugin that moves locked assets out of a drained EVM wallet in one EIP-7702
transaction paid by a fresh operator, with Gas.zip gas fan-out and timed unlock rescue.

**Architecture:** pure Python core (`core/`) with no Hermes imports, wired to Hermes by a thin
layer (`__init__.py`, `schemas.py`, `tools.py`). Contracts are Solidity compiled by Foundry; the
plugin ships their ABI and bytecode as a JSON text artifact. Tests run the core against
`anvil --hardfork prague`.

**Tech Stack:** Python 3.11, web3 7.x, eth-account 0.13.x, requests, pytest, Foundry (forge,
anvil), solc 0.8.28.

**Spec:** `docs/superpowers/specs/2026-11-09-lifeboat-design.md`

## Decisions made after the spec

These came out of plan research on 2026-11-09 and change the spec slightly:

1. `RescueBatch` gains self-call helpers `sweepERC20(token, to)` and `sweepNative(to)` so a batch
   moves the balance that exists at execution time ("all"), not an amount guessed at plan time.
   Vesting balances grow every block, and a fixed amount that is too high reverts the whole
   batch. The helpers require `msg.sender == address(this)`, which only the batch itself or the
   key holder can satisfy, and the key holder can already move the tokens directly.
2. `RescueBatch` implements `onERC721Received`, `onERC1155Received`, `onERC1155BatchReceived`.
   Once delegated, the victim has code, so any `_safeMint` or safe transfer to it calls these
   hooks and reverts without them.
3. Simulation overrides the victim's code with the RescueBatch runtime code itself (immutable
   operator patched in locally from the artifact's `immutableReferences`), not with a
   delegation designator. This works on any RPC that supports `eth_call` state overrides.
   A second contract, `RescueSim`, is used only as override code to report per-call results and
   balances in one call. It is never deployed.
4. Gas.zip quotes return a ready `contractDepositTxn` (`to`, `data`, `value`). The plugin sends
   that, after checking `to` against a pinned deposit contract, `value` against the requested
   amount, and that `data` names the operator. No testnet can be a Gas.zip deposit source, so a
   testnet fan-out is funded from a mainnet (observed: 0.0015 ETH on Base gives about 4.5 ETH on
   each of Base Sepolia and OP Sepolia; Base Sepolia minimum outbound is $1).
5. The arm watcher is an in-process daemon thread started under `contextvars.copy_context()`
   (secret scope is a ContextVar), stopped through `ctx.on_unload`, and resumed from stored jobs
   when the plugin loads. Hermes must stay running until the unlock; status says so.
6. New write tool `lifeboat_sweep_back`: returns leftover operator gas to the safe address,
   approval-gated like the others.
7. Redaction registers the exact key strings as escaped literals, not a generic 64-hex pattern,
   which would also redact transaction hashes.
8. `priority_gwei` defaults to the node's suggested tip, not 2 gwei. Measured on Gensyn mainnet: gas
   price 0.001 gwei, so a 2 gwei tip would cost about 2000 times the fee. A caller that races a
   mempool-watching sweeper on Ethereum passes an explicit value.
9. OP Stack chains take a data fee from the sender's balance on top of gas. Balance checks and the
   sweep-back reserve read `GasPriceOracle.getL1Fee` (0 where the oracle does not exist).
10. `execute` raises only before sending (`ExecuteRefused`, `SimulationFailed`,
    `InsufficientOperatorFunds`) or when no receipt arrives (`NotConfirmed`, carrying the hash). Once a
    receipt exists it returns a `Receipt` whose `ok` is False and whose `problems` say what the chain
    does not show, because a type 4 transaction with a stale authorization still succeeds on chain.
11. Error text leaving the core goes through `strip_urls`: provider URLs carry API keys.
12. Gensyn mainnet (chain 685689) is in the chain table. Checked 2026-11-09 with a live `eth_call` that
    carries an authorization list: delegation is honoured, and public RPC accepts state overrides.
13. Task 6 registers only the tools whose core exists: `lifeboat_plan`, `lifeboat_simulate`,
    `lifeboat_status`, `lifeboat_execute`, `lifeboat_sweep_back`. The validator requires declared
    tools to match registrations, so `lifeboat_scan`, `lifeboat_fund_gas` and `lifeboat_arm` join the
    manifest in Tasks 7 to 9.
14. The data directory is `ctx.state.data_dir`, resolved on every call because one Hermes process can
    serve several profiles. Secrets are read with `agent.secret_scope.get_secret`.
15. The approval hook reads stored state only (no RPC) and blocks a plan without a passing stored
    simulation. `lifeboat_simulate` stores a gas ceiling next to the verdict, and the approval text
    shows it. Each approval carries a unique `rule_key`, because the gate's "always" answer is keyed
    on it.
16. `hermes plugins validate . --install-deps` passes, security scan included, with
    `contracts/artifacts.json` shipped as is. This closes spec open check 5.

## Changes after the security review (2026-11-09)

An independent review of commit 0ec2e23 reproduced one critical flaw and several medium ones on a
local anvil. `tests/test_audit.py` holds a regression test for each; all failed before the fix.

17. A `call` action can no longer grant power over assets: every approval, permit, operator
    authorization, callback transfer and nested multicall selector is refused. This supersedes the
    earlier rule that allowed an approval for a later call target. A rescue that needs an approval
    before an unstake is out of scope for v1.
18. Simulation also watches, as ERC-20s, every call target and every address passed in calldata. A
    watched token that leaves the wallet without reaching the safe fails the plan.
19. Every asset planned for transfer must arrive at the safe address; a plan that moves nothing fails.
    The fee-on-transfer shortfall stays a warning only in a plan without `call` actions, where the
    token itself is the only thing that can take a share. With a `call` in the plan it is a failure.
20. `execute` compares its fresh simulation with the approved one stored on the plan and refuses when
    the safe would receive less. After the transaction, arriving short of the simulation is a problem.
21. The approval line for a `call` starts with a fixed `CALL to`, shows the calldata and the addresses
    it names, and quotes the agent's description last, so it cannot pass for a built-in step.
22. The hook blocks when Hermes would skip its prompt (yolo mode or approvals off). The probe reads
    two private Hermes functions and fails closed when they cannot be read.
23. A stored plan is rebuilt from its actions on every load and refused when its calls or labels
    differ. The plan's victim must be the configured wallet and its operator one lifeboat holds.
24. The safe address may not be the drained wallet or an operator wallet.
25. Once the transaction bytes are sent, any failure reports the locally computed hash
    (`NotConfirmed`). Only an explicit node rejection counts as not sent.
26. `execute` and `ensure_batch` refuse a transaction that could cost more than the approved gas
    ceiling, which carries 25% headroom over the estimate.

Known limit, accepted for v1: a `call` to a contract that already holds an allowance from the wallet,
for a token that is neither planned, nor the call target, nor named in the calldata, is not seen by
the delta check. The approval text shows the call and its calldata; nothing else stops it.

## Changes after the second security review (2026-11-10)

A wider review of commit 1525d09 confirmed 26 findings, 7 of them high; `docs/security-review.md`
keeps the summary. The fixes below supersede items 17, 18, 20, 21, 22 and 25 where they differ.
Regression tests are in `tests/test_review2.py`, `tests/test_plan_policy.py` and
`tests/test_keys.py`. Each was checked by breaking the behaviour it covers and seeing it fail.

27. A `call` is written as a function signature and typed arguments, never as raw calldata. Only
    `address`, `bool`, `uintN`, `intN`, `bytesN` and flat arrays of them are accepted, so `bytes`,
    `string`, tuples and every nested-call shape cannot be expressed. Every address argument must be
    the drained wallet, the safe address or a token the plan transfers; the recipient of a transfer
    function must be the safe. This replaces the calldata word scan, which could be dodged.
28. A plan needs at least one transfer step. A call alone leaves nothing whose arrival can be
    checked, so a claim that pays the safe directly still names the asset it pays.
29. `RescueBatch.execute` takes a list of conditions and reverts the whole batch when the safe address
    receives less than a person approved: a balance that must grow by a minimum, an NFT owner, a
    native balance. A dry run can be told apart from the real transaction by a hostile target (the
    simulated wallet carries full code, the real one a 23-byte designator), so the promise is
    enforced on chain. The minimums are the approved amounts, not the ones of a later dry run.
30. The native currency is an asset like the others: it has a balance line, must arrive, and gets a
    condition. A transaction that lands without the delegation being applied is never reported as a
    rescue.
31. Only the target of a `call` is watched as a token. When the wallet's balance on it drops (an
    unstake, a redeem, an unwrap), the plan passes only if a planned asset reaches the safe in a
    larger amount than the wallet held, and the drop is shown as a warning in the approval text.
32. Nothing a person approves is read back from the data directory. The simulation shown in the
    prompt is the one the process ran and kept in memory; an approval is a record in memory, bound to
    a digest of the plan, to the approved amounts and to the gas ceiling, used once and for fifteen
    minutes. The handler refuses a call without that record. A restart means simulating again.
33. An operator key file holds the key sealed, and carries a MAC, both under a secret derived from the
    victim key. A file lifeboat did not write is ignored. Recovering an operator by hand needs the
    victim key.
34. The gate probe also blocks sessions where nobody can answer (cron, `-q`, webhook, API) and the
    plugin host process, where a session's yolo switch cannot be seen.
35. Redaction patterns keep two literal characters and match a key with or without `0x`. Hermes
    forbids an identifier character before a match and prints a pattern's literal start in its
    marker, so the earlier fully literal pattern missed the `0x` form and echoed the bare one.
36. A send is never retried by the client. An error from the node is checked against the transaction
    hash before it counts as "not sent".
37. The rescue carries one authorization per nonce the victim may reach (mined to pending, at most
    four), so a victim transaction left waiting in the pool cannot void it.
38. Sweep-back measures the gas when the safe address runs code, and sends nothing when the safe
    would reject the transfer.

## The misuse gate (2026-11-10)

39. lifeboat sends a rescue only for a wallet with a sweep on record (`core/evidence.py`). Its one
    real use is a wallet where gas is taken as soon as it arrives; any other wallet can be funded
    and emptied the ordinary way, and a tool that moves another wallet's staked and vesting
    positions on the strength of a key alone is a drainer. Evidence is two incoming native
    transfers that left again to another address within 300 seconds for at least half the amount.
    A delegation alone is not evidence, because wallet apps delegate accounts to their own
    contracts; what a sweeper contract forwards is read from the explorer's internal calls.
40. Evidence counts per key, not per chain. A leaked key is leaked everywhere, so a sweep seen on
    any chain unlocks the rescue on every chain, and the asset a sweeper has not found yet stays
    rescuable. `lifeboat_simulate` looks, the plan's own chain first; the approval hook blocks a
    plan without evidence and the approval text quotes it. There is no switch to turn the gate off.
41. Looking is read-only. Nothing is ever sent to the drained wallet to see whether it gets swept:
    that would wake the sweeper on a chain it has not touched. Until the rescue transaction itself,
    nothing lifeboat does on a chain involves the drained wallet's address: the operator is a
    fresh wallet, and the batch is deployed from it. The operator must not be funded from the
    drained wallet either, since that is a transaction from it.
42. Evidence found once is stored with a tag under the secret derived from the victim key, because
    only the latest pages of a history are read and explorers go down. A stored record without a
    valid tag is ignored.
43. History comes from each chain's Blockscout API (`/api/v2/addresses/<address>/transactions`, two
    pages). Checked live on 2026-11-10: Base Sepolia, OP Sepolia, Sepolia, OP Mainnet, Ethereum and
    Gensyn answer. `base.blockscout.com` answers scripts with a browser challenge, so Base has no
    readable history and sweeps there cannot be seen. A chain that cannot be read is reported
    and never hides another.

44. Twelve chains were added on 2026-11-10 (Arbitrum One and its Sepolia testnet, Robinhood Chain,
    Unichain, Soneium, Ink, World Chain, Scroll, Gnosis, Linea, Berachain, Sonic), each after a live
    probe: chain id, `eth_call` and `eth_estimateGas` with an EIP-7702 authorization, `eth_call` with
    a state override, then lifeboat's own fee and deployment-estimate code. Probed and left out:
    zkSync Era, Zora and Mode (delegation not honoured), BNB Chain and Polygon (web3 cannot read
    their blocks without extra middleware, and their fee rules are untested here), Lisk (RPC down).
    One chain in the table has seen a real rescue; the others are supported on the strength of the probe.

Limits of the gate. It proves a sweep, not ownership: the owner and a thief hold the same key. A
thief can stage the pattern with two small transfers, so the gate stops first-strike use on an
untouched wallet and casual misuse, not a determined one. The pattern detector has been
run against synthetic histories and against live explorer responses for an ordinary address, not
yet against the history of a really swept wallet.

Known limits, accepted for v1. A call target that is itself hostile can still pay an address fixed
in its own code: lifeboat only guarantees that the planned assets reach the safe in the approved
amounts, or nothing happens. A token the wallet holds that is not in the plan is not watched, so a
target holding an old allowance for it can take it; the scan in Task 7 is what puts every held
token into the plan. Naming a planned token as the receiver of a withdrawal passes the policy and
would strand the funds in that token contract; the approval line labels every address with its
role for that reason.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.28;

abstract contract RescueCore {
    function sweepERC20(address token, address to) external {
        require(msg.sender == address(this), "self only");
        (bool ok, bytes memory ret) = token.staticcall(abi.encodeWithSelector(0x70a08231, address(this)));
        require(ok && ret.length >= 32, "balanceOf failed");
        uint256 bal = abi.decode(ret, (uint256));
        if (bal == 0) return;
        (ok, ret) = token.call(abi.encodeWithSelector(0xa9059cbb, to, bal));
        require(ok && (ret.length == 0 || abi.decode(ret, (bool))), "transfer failed");
    }

    function sweepNative(address payable to) external {
        require(msg.sender == address(this), "self only");
        uint256 bal = address(this).balance;
        if (bal == 0) return;
        (bool ok, ) = to.call{value: bal}("");
        require(ok, "native send failed");
    }

    function onERC721Received(address, address, uint256, bytes calldata) external pure returns (bytes4) {
        return 0x150b7a02;
    }
    function onERC1155Received(address, address, uint256, uint256, bytes calldata) external pure returns (bytes4) {
        return 0xf23a6e61;
    }
    function onERC1155BatchReceived(address, address, uint256[] calldata, uint256[] calldata, bytes calldata)
        external pure returns (bytes4)
    {
        return 0xbc197c81;
    }
    function supportsInterface(bytes4 id) external pure returns (bool) {
        return id == 0x01ffc9a7 || id == 0x150b7a02 || id == 0x4e2312e0;
    }

    receive() external payable {}
}
```

`RescueBatch is RescueCore`: `struct Call {address to; uint256 value; bytes data;}`,
`address public immutable operator`, constructor sets it, `execute(Call[] calldata)` requires
`msg.sender == operator` and bubbles the first revert. `RescueSim is RescueCore`:
`struct Probe {address target; bytes data;}`,
`simulate(Call[] calldata calls, Probe[] calldata probes) external payable returns (bool[] memory ok, bytes[] memory ret, bytes[] memory probeRet, uint256 nativeAfter)`
runs every call without stopping, then staticcalls every probe. Fixtures: `MockToken` (ERC-20 with
`mint`), `MockNFT` (ERC-721 with `safeMint`), `MockStaking` (`stake(amount)`,
`withdraw()` returns tokens and `claimReward()` that `_safeMint`s an NFT receipt to the caller),
`MockVesting` (`claim()` reverts before `unlockTime`, then transfers the vested tokens).

### Task 4: Simulation

**Files:**
- Create: `core/simulate.py`
- Test: `tests/test_simulate.py`

**Interfaces:**
- Consumes: `Plan`, `core.artifacts`.
- Produces: `simulate(w3, plan, artifacts) -> SimResult` with `ok: bool`, `revert_reason: str | None`
  (from the real-batch call), `calls: list[CallResult(ok, reason)]` (from RescueSim),
  `balances: list[BalanceDelta(asset, victim_before, victim_after, safe_before, safe_after)]`,
  `native_after: int`, `deltas_ok: bool`, `block: int`.

How it runs:
1. Probes for every planned ERC-20 (`balanceOf(victim)`, `balanceOf(safe)`), ERC-721
   (`ownerOf(id)`) and ERC-1155 (`balanceOf(holder, id)`).
2. "Before": `eth_call` of `RescueSim.simulate([], probes)` with the victim's code overridden by
   `sim_runtime()`.
3. "Detail": same override, `simulate(calls, probes)`.
4. "Real": override victim code with `batch_runtime(plan.operator)`, `from = operator`,
   `to = victim`, `data = encode_execute(calls)`. Its success or revert reason is the verdict.
5. `deltas_ok` fails when an NFT does not end at the safe, or when the victim loses a token and
   the safe gains none of it. A safe gain smaller than the victim's loss (fee-on-transfer, or a
   share going elsewhere) is a warning shown in the approval text, not a failure, because fee
   tokens are common and blocking them would strand the rest of the rescue.
6. `ok = real succeeded and deltas_ok`. If the RPC rejects state overrides, raise
   `SimulationUnavailable` with the RPC's message; execute refuses without a passing simulation.
