# lifeboat: design

Date: 2026-11-09. Target: Hermes Agent Plugin Hackathon, deadline 2026-11-11 22:00 UTC.

## Problem

When a private key leaks, a sweeper bot takes everything that can move on its own: native gas and
free tokens. What stays behind needs a transaction first: an airdrop claim, a vesting unlock, a
staked or LP position. Every bit of gas sent to the victim wallet to pay for that transaction is
swept within a block. Owners give up on assets that are still recoverable, or download "rescue
scripts" that steal from them a second time.

lifeboat is a Hermes plugin that gets those assets out without the victim wallet ever holding gas.

## Core technique

EIP-7702. A fresh operator wallet sends one type-4 transaction that carries an authorization
signed with the victim key. The authorization points the victim EOA at `RescueBatch`, a small
contract whose `execute(Call[])` only obeys the operator. In the same transaction the victim EOA
runs the batch: claim, withdraw, transfer everything to the safe address. The operator pays the
gas. The victim never holds any.

A delegation does not take the leaked key's power away: the sweeper can still send transactions
from the victim or re-delegate it. lifeboat wins by never giving the sweeper a window, not by
locking it out. Reports say so.

## Safety model

| Item | Where it lives | Why it is low risk |
|---|---|---|
| Victim key | `LIFEBOAT_VICTIM_KEY`, `requires_env` secret, read with `agent.secret_scope.get_secret` | Already leaked; holding it exposes nothing new |
| Operator key | Generated by the plugin per rescue, stored in plugin data | Holds only the gas the user deposits; swept back afterwards |
| Safe address | `LIFEBOAT_SAFE_ADDRESS`, config only | Never a tool argument, so a prompt injection cannot redirect funds |

Rules:

1. No tool takes a key as an argument; no tool output, log line or error contains one. Redaction
   patterns are registered as a second net. Tests prove both.
2. Every recipient is the configured safe address. Plans that send elsewhere are rejected.
3. Gas is never sent to the victim address. The plugin refuses.
4. Read-only by default. Without `LIFEBOAT_ENABLE_EXECUTE=1`, the funding, execute and arm tools
   are not registered (`check_fn`).
5. Every transaction goes through Hermes approval: a `pre_tool_call` hook returns
   `{"action": "approve", "message": <exact plan summary>}` for `lifeboat_fund_gas`,
   `lifeboat_execute` and `lifeboat_arm`. Unattended runs fail closed.
6. Every batch passes simulation before it can be sent.

Worst case: the user loses the gas deposit.

## Tools

| Tool | Writes? | Does |
|---|---|---|
| `lifeboat_scan` | no | Per chain: native balance, ERC-20/721/1155 holdings, existing 7702 delegation (`0xef0100` code), recent sweeper activity |
| `lifeboat_plan` | no | Builds a batch from actions (`transfer_erc20`, `transfer_nft`, `call` with user-supplied target and calldata for claims and withdrawals); returns a plan id and a human summary |
| `lifeboat_simulate` | no | Runs the batch with `eth_call` state overrides as if the victim were delegated; reports per-call success and resulting balances |
| `lifeboat_fund_gas` | yes | One native deposit from the operator, split by Gas.zip to the selected chains; waits until gas arrives on each |
| `lifeboat_execute` | yes | Deploys `RescueBatch` if missing, signs the authorization, sends the type-4 transaction with a high priority fee, verifies balances |
| `lifeboat_arm` | yes | Unlock mode: stores a job for a known unlock time, wakes shortly before it, polls blocks and fires in the first block at or after the unlock; re-signs the authorization if the victim nonce moved |
| `lifeboat_status` | no | Jobs, armed unlocks, receipts, before/after balances, explorer links; offers the operator sweep-back |

Slash command `/lifeboat` walks a person through scan, plan, simulate, fund, execute.

## Gas fan-out (Gas.zip v2, checked 2026-11-09)

- `GET https://backend.gas.zip/v2/chains`: 186 chains, 61 testnets; per-chain min/max in USD.
- `GET https://backend.gas.zip/v2/quotes/{deposit_chain}/{deposit_wei}/{outbound_chains}?to=&from=`:
  per-chain quotes. Observed: one chain can fail ("Insufficent Liquidity") while the rest quote.
- Deposits are native sends to a per-chain Direct Deposit address with calldata naming the
  destinations, $0.25 to $50 per deposit.
- Addresses flagged by their screening provider are refused. The operator is always fresh.

The flow scans first and funds only chains with something worth rescuing (default), a manual
list, or every supported chain with a cost warning.

## Out of scope for v1

Chains without EIP-7702 (permit fallback), automatic airdrop discovery, Flashbots bundles,
auto-sell after rescue, non-EVM chains. Positions are not discovered generically: the user
supplies the withdraw or claim call, and the plan simulates it.

## Testing

- pytest against `anvil --hardfork prague`: rescue an ERC-20, an NFT and a staked position from a
  victim whose ETH is swept every block by a simulated sweeper; timed rescue of a token that
  unlocks at a set timestamp.
- Leak tests: no key in any tool result, log record or exception text.
- Policy tests: recipient cannot be changed, gas to the victim is refused, write tools are absent
  without the execute flag, the approval hook fires for every write tool.
- Build check: the shipped `RescueBatch` artifact matches a fresh compile of the source.

## Demo (under 90 seconds)

Base Sepolia. A victim wallet with a vesting token and a staked position, a sweeper bot from
`demo/` taking every wei that arrives. Scan table, one deposit fanned out, one transaction that
moves everything while the sweeper gets nothing.

## Open checks before or during build

1. Blockscout v2 token endpoints per chain (scan source).
2. Whether public RPCs accept a delegation designator in `eth_call` state overrides, or only
   plain runtime code (simulation path).
3. Gas.zip deposit calldata format (calldata builder page) and deposit address per chain.
4. Long-lived watcher for `lifeboat_arm`: `ctx.spawn_task` in the gateway process versus a cron
   job; `register_background_service()` is still an open core issue (#63721).
5. Whether `hermes plugins validate` accepts a compiled contract artifact (catalog rule 17).
